## 3. Три уровня портфолио

### Уровень 1 — Flagship / System-level
Доказывают способность строить полноценные системы: состояние, роли, БД,
бэкенд, авторизация, аналитика. Именно они должны быть «выше сгиба» и
получить героев на Home/Works.

1. **pet-project-CRM** — React/TS + Node/Express + PostgreSQL/Prisma, RBAC,
   Kanban, аналитика. *(уже на сайте, но не выделен — поднять в топ)*
2. **Coin Collector System (coin_set + coinset-api)** — Kotlin Android app +
   FastAPI/PostgreSQL backend с миграциями, JWT, admin-панелью.
   *(отсутствует на сайте — добавить как новый flagship-кейс, после того как
   от владельца будут получены скриншоты/README)*
3. **AI Space** (aispace, Vue3/TypeScript) — как минимум продуктовый
   AI-инструмент с чатом/фичами, ближе к System-level, чем к простому
   лендингу, за счёт интерактивности и TS. *(уже на сайте — подтянуть на
   уровень 1 или пограничный 1.5)*

### Уровень 2 — Product sites
Лендинги/сайты, сделанные для реальных внешних заказчиков — доказывают опыт
коммерческой работы с клиентами.

- **Whale Business** (`crossplatform`, whalebiz.co.il) — React, есть логин/
  регистрация — заметно сложнее обычного лендинга (пользовательские сценарии
  входа), реальный работающий сайт клиента.
- **Landfolio** (daria-levitan.com, Vue3) — портфолио-сайт для клиента,
  живой домен.
- **Change Web / money-site** — Vue3, задеплоен на S3, живой сайт.

### Уровень 3 — Craft / Quick builds
Небольшие, учебные или демонстрационные работы — важны для объёма портфолио
и разнообразия стека, но не должны конкурировать за внимание с flagship.

- `android` (первое Android/Java-приложение)
- `cross_II` (React Native)
- `learning` (React, учебный проект)
- `massage` (статический HTML/CSS/JS-лендинг)
- Опционально, при желании расширить AI/бэкенд-направление: `TG_bot`,
  `CalendarBot` — как «сайд-проекты», показывающие интерес к AI-интеграциям.

**Обоснование деления:** критерий — не «сколько экрана/файлов», а *наличие
состояния, ролей, авторизации, собственного бэкенда/БД и жизненного цикла
данных*. CRM и Coin Collector System — единственные два проекта с
полноценной серверной частью, ролевой моделью и персистентным хранилищем.
Всё остальное — либо статические/презентационные сайты (даже стильные), либо
фронтенд без своего бэкенда. Это ровно та грань, которую сейчас не видно на
сайте и которую нужно визуально закрепить (например, бейджи "System" /
"Product site" / "Craft" на карточках Works).

## 4. Тексты кейсов (флагманы)

### Кейс 1 — pet-project-CRM
**Проблема.** Малому/среднему бизнесу нужен единый инструмент для ведения
клиентов и сделок вместо разрозненных таблиц: без контроля стадий сделки,
без разграничения прав между менеджерами и админом, без аналитики по
менеджерам и выручке.

**Решение.** Полноценная CRM-система с Kanban-доской сделок (drag-and-drop
по стадиям пайплайна), карточками клиентов с историей взаимодействий,
задачами с дедлайнами, тремя уровнями доступа (администратор / менеджер /
наблюдатель) и дашбордом аналитики (конверсия, выручка, эффективность
менеджеров).

**Стек.** Frontend: React + TypeScript, Redux Toolkit, Material UI,
Recharts. Backend: Node.js + Express, JWT-аутентификация, валидация Zod.
База данных: PostgreSQL + Prisma ORM. Деплой: Docker Compose. Документация
API: Swagger.

**Результат / что демонстрирует.** Демонстрирует владение полным
production-циклом full-stack разработки: типизированный фронтенд с
менеджментом состояния, защищённый REST API, ролевую модель доступа,
контейнеризацию и работу с реляционной БД через ORM. *Метрики использования
(реальные пользователи, конверсия и т.п.) — требуется уточнение у владельца,
если проект использовался в продакшене; иначе позиционировать как
демонстрационный pet-project профессионального уровня.*

### Кейс 2 — Coin Collector System (coin_set + coinset-api)
**Проблема.** Коллекционерам монет нужен инструмент для каталогизации
коллекции (по странам/правителям/монетам), который работает как нативное
мобильное приложение и синхронизирует данные через собственный сервер, а не
просто хранит записи локально.

**Решение.** Двухкомпонентная система: нативное Android-приложение на
Kotlin (Jetpack Compose) для просмотра каталога и ведения личной коллекции,
и отдельный backend на FastAPI с иерархической моделью данных
«страна → правитель → монета», продвинутым поиском/фильтрацией по металлу и
редкости, загрузкой изображений и админ-панелью со статистикой.

**Стек.** Клиент: Kotlin, Jetpack Compose, Android Studio. Backend: FastAPI,
PostgreSQL, SQLAlchemy, Alembic (миграции), Pydantic, JWT-аутентификация,
Docker.

**Результат / что демонстрирует.** Единственный в портфолио пример полного
цикла «нативный мобильный клиент + собственный REST API + БД с миграциями»
— то есть mobile + backend engineering, а не только frontend. Показывает
умение проектировать доменную модель и API с нуля. *Живого демо/деплоя
backend, а также скриншотов приложения на момент аудита в репозиториях нет —
требуется уточнение и материалы у владельца перед публикацией кейса.*

### Кейс 3 — AI Space
**Проблема.** Нужен инструмент/интерфейс для работы с AI-функциями
(предположительно чат/AI-фичи, судя по структуре `aispace_chat.png` в
текущих ассетах сайта) с современным, типизированным фронтендом.

**Решение.** Продуктовый интерфейс на Vue 3 + TypeScript с отдельным
чат-экраном и блоком фич — согласно уже существующим скриншотам на сайте
(`aispace_home.png`, `aispace_chat.png`, `aispace_features.png`).

**Стек.** Vue 3, TypeScript, CSS3.

**Результат / что демонстрирует.** Владение TypeScript в связке с Vue 3 и
опыт проектирования интерфейсов для AI-продуктов — актуальное и востребованное
направление. *Точное назначение приложения, есть ли у него реальный бэкенд/
AI-интеграция (или это чисто UI-прототип) — требует уточнения у владельца:
это существенно меняет, отнести ли кейс к Уровню 1 (System-level) или
понизить до Уровня 2/3.*

### Кейс 4 — Whale Business (crossplatform)
**Проблема.** Реальному бизнес-клиенту (whalebiz.co.il) нужен был
работающий веб-сайт с пользовательскими сценариями входа/регистрации, а не
статическая визитка.

**Решение.** React-приложение с публичным лендингом и экранами логина/
регистрации пользователя — то есть с базовой пользовательской сессией, а не
только контентными страницами.

**Стек.** React, JavaScript, CSS3.

**Результат / что демонстрирует.** Реальный, ныне живой клиентский сайт
(лучшее доказательство коммерческого опыта в текущем портфолио на уровне
Product site) с элементами, выходящими за рамки чистого лендинга (auth-
экраны). *Метрики бизнеса клиента (трафик, конверсии) — требуется уточнение
у владельца.*

## 6. Структура уровней для Services

Технически на странице уже есть сетка на 4 карточки (`services.s1..s4` в
`Info.comp.jsx`) — предлагаю наполнить её именно этой лестницей уровней
(без цифр/цен — по явному ограничению задачи):

1. **Landing Page** — Одностраничный сайт-визитка: быстрый запуск,
   адаптивная вёрстка, форма обратной связи. Подходит, чтобы быстро выйти в
   сеть с минимальным бюджетом.
2. **Business Site** — Многостраничный сайт для бизнеса: каталог/услуги,
   мультиязычность, интеграции (формы, карты, аналитика). Подходит, когда
   визитки уже недостаточно и нужна полноценная витрина.
3. **Web App** — Интерактивное веб-приложение с пользовательскими сессиями,
   личным кабинетом и собственным API/бэкендом. Подходит бизнесу, которому
   нужен инструмент, а не просто сайт (авторизация, работа с данными
   пользователя).
4. **CRM / System** — Система под ключ: роли и права доступа, база данных,
   аналитика/дашборды, интеграции с внешними сервисами. Подходит компаниям,
   которым нужно автоматизировать внутренние процессы (продажи, коллекции
   данных, учёт).

Каждый уровень стоит визуально привязать к конкретному кейсу-доказательству
из раздела 4 (Landing → massage, Business Site → Landfolio/Whale Business,
Web App → AI Space, CRM/System → pet-project-CRM и Coin Collector System) —
это превращает Services из абстрактного прайса в доказательную лестницу.

## 7. Конкурентный ресёрч — что перенять по структуре подачи

На основе анализа паттернов топовых портфолио разработчиков/студий и
рекомендаций по фриланс-кейсам 2025-2026:

1. **Кейс = мини-история, а не скриншот с подписью.** Структура
   Problem → Approach → Result читается лучше, чем просто "технологии:
   React, Node" под картинкой — именно её мы закладываем в раздел 4.
2. **Явная иерархия важности.** Сильные студийные портфолио выносят 1-3
   "hero"-проекта крупным блоком на первый экран, остальное — в компактную
   сетку/архив ниже. Сейчас у land_site все 9 проектов равны по весу — это
   стоит сломать.
3. **Измеримый результат, где он есть, честная пометка, где его нет.**
   72% нанимающих (по опросам про 2025 год) дольше задерживаются на
   портфолио с детальными кейсами, чем на голых галереях — но выдуманные
   цифры хуже, чем их отсутствие; лучше явный CTA "спросить у автора" или
   техническое описание архитектуры как замена метрике.
4. **Разделение по типу, а не только по хронологии.** Топовые портфолио
   фильтруют работы по типу продукта/сложности (например, "Web App" /
   "Landing" / "Mobile"), а не просто листают в хронологическом порядке —
   ровно то, что мы предлагаем в п.3 и п.6.
5. **Живые ссылки и репозитории — обязательны, если есть.** Проекты со
   ссылкой на живое демо или GitHub конвертят заметно лучше "просто
   картинки" — у нас это уже частично есть (`siteUrl`/`github` в
   `projectsData.js`), но для `coin_set`/`coinset-api` этого пока нет —
   стоит запросить у владельца хотя бы деплой Swagger UI backend.
6. **Стек — не список иконок, а объяснение выбора.** Сильные кейсы поясняют
   *зачем* выбран стек под задачу (например, "Prisma+PostgreSQL — для
   строгой схемы данных в CRM"), а не просто перечисляют технологии — это
   встроено в тексты кейсов раздела 4.
7. **3-5 проектов, показывающих диапазон навыков, лучше, чем 9 похожих.**
   Рекомендация из индустрии — не разбрасываться количеством, а подобрать
   выборку, покрывающую разные грани (frontend, backend, mobile, AI). У нас
   после добавления Coin Collector System такой диапазон уже есть — стоит
   не размывать его дополнительными мелкими лендингами на первом экране.
8. **About/Resume как отдельный слой доверия.** Учебные репозитории
   (Data Structures, Middleware homework и т.п.) не место в Works, но могут
   усилить About как показатель системного обучения/роста — если владелец
   захочет такой раздел.

## 9. Дополнение (запрос владельца, 2026-09-22): AI как отдельная услуга

Владелец явно попросил добавить в позиционирование **AI-интеграции как
предложение услуги**, отдельно от портфолио-кейсов: способность встраивать
AI-чат-ассистентов на клиентские сайты и внедрять AI в системы уровня CRM
(например, для прогнозирования/аналитики, помощи в принятии решений и т.п.).

Важно подать это честно — как **техническую компетенцию/предложение**, а не
как «уже сделанный кейс с метриками» (реальных клиентских AI-CRM кейсов пока
нет). Доказательная база для этого в портфолио уже есть: AI Space
(Vue3/TS, чат-интерфейс), TG_bot (AI-генерация изображений, очереди задач,
PyTorch), CalendarBot (голос → календарь через Whisper+OpenAI) — их стоит
использовать как proof-of-capability для этой услуги, а не заявлять AI как
уже интегрированный в pet-project-CRM.

Рекомендация для Services (добавить как 5-й уровень/дополнение к лестнице из
раздела 6, либо как отдельный акцент внутри уровня "CRM / System"):

5. **AI-интеграции** — Внедрение AI-функциональности в сайты и системы:
   чат-ассистенты для поддержки клиентов на сайте, AI-аналитика и
   прогнозирование внутри CRM/дашбордов (например, прогноз выручки, скоринг
   сделок), автоматизация на основе LLM. Подходит бизнесу, который хочет не
   просто автоматизировать процессы, а сделать их «умными».

Рекомендация для Home/About: добавить одну фразу к позиционированию,
явно называющую AI как часть стека (например: «...а также встраиваю
AI-возможности — чат-ассистентов и прогнозную аналитику — в сайты и
CRM-системы»), без обещания конкретных результатов, которых нет.
